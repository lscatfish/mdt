### 0.4 实验性质说明：许愿式生成

**任务提示词原文**（十一会话完全一致，一条用户消息）：

> 你只能够修改当前目录下的文件，可以使用 git 进行版本管理。请复刻一个网页版本的我的世界游戏

（各预设的系统提示与注入差异见第 1 节；会话还含一条 harness 环境消息"approval policy changed from ask to never"，非任务内容。）

**什么是"许愿式生成"**：本次实验的统一性质定义——**指令层**没有工程脚手架：任务提示词只提出愿望式目标（"复刻一个网页版本的我的世界"），无验证指令、无质量标准、无技术选型约束、无验收清单、无工程规范注入。模型拿到的是"目标 + 当前目录 + git 权限"，技术路线、功能面、验证方案全部由模型自主决定。

**但环境层自带能力脚手架（用户预装，非实验变量）**：
- **4 个 MCP 服务器**（晋升后全部进入工具目录，共 36 个工具）：playwright（浏览器自动化，24 工具）、server-memory（会话记忆知识图谱，9）、context7（库文档查询，2）、codegraph（代码检索，1）；
- **项目 skill 目录注入（Matt Pocock 的 skills 集）**：用户安装的 Matt Pocock skills，RL-open 会话实测注入 15 项（code-review / tdd / grilling / diagnosing-bugs / prototype / research / wizard / writing-for-agents 等，数量随项目目录的 skill 目录而异）；
- 因此"许愿式生成"的准确含义是：**指令层零工程要求，环境层脚手架齐备**。验证文化的工具基础正是这个脚手架——playwright 使像素断言/控制台检查成为可能；模型的自主性体现在**在无任何提示下选择使用**（RL 调用 playwright 74 次，codegraph/context7/server-memory/skill 0 次——脚手架可用，用不用、怎么用由模型决定）。anchored 系预设首轮只暴露 2 个工具（MCP 不可见），晋升后才可见可用。

**它的规划性质：短程规划，不是长程规划**。生成过程确实带有规划，但形态是：
- **前期一次性架构设计**（如 RL step 3 的 65k 字符设计块、B1/UP 的深首块）——把功能面/文件结构/技术路线一次性定下来，之后进入执行；
- **逐块"思考-行动"交替的局部决策**——每个推理块闭合后立即调用工具，决策窗口只有"下一两个动作"（宏观结论第 3 条：完成度来自逐块闭合，不来自全局计划）；
- **没有长程规划**：无计划状态维护（todo_write 极少且不持续）、无里程碑跟踪、无跨阶段约束保持（B+T 中断 4 小时后风格要求失效 = 短程约束衰减的直接证据；RL 执行中大量涌现式局部调整——出生点水下、游泳浮力等 step 61–74 均为执行时的新决策）。
- 一句话：**愿望式目标 → 一次性设计 → 短程逐块执行**，全程没有"长期计划"这个状态被维护。

**我们没有做什么**：没有针对"工程能力"设计对照实验——全部干预变量都是表达层/工具面变量（说话风格要求、锚定工具对、输出 cap、注入方式），没有一个是工程能力类干预。因此本报告结论应被读作：**模型在"指令层无工程脚手架、环境层有 MCP/Skill 能力脚手架"下的原生工程能力表现**。

**工程能力评价：还是可以的**：
- **11/11 会话都交付了可运行产物**（git 提交 + 本地启动可玩），无一中途放弃或不可启动；
- **6/11 获得中等以上评级**（最好 2：B1/UP；较好 2：B3/RL；中等 1：B+T；还行 1：PA——黑屏由用户一行修复后）；
- **两条技术路线都完整走通**：零依赖自研（B1 90KB 自研渲染、PA 88KB + 26 单元测试）与 three.js 模块化（7–8 文件：噪声/世界/网格/玩家/游戏/方块）均实现完整功能面（程序化地形、区块流式、AABB 碰撞、方块交互、昼夜循环、存档）；
- **验证行为原生具备（工具来自脚手架）**：在 playwright MCP 可用下，playwright 自动化验证普遍出现（像素断言、控制台零错误、物理模拟），多数会话在无任何提示下自主完成验证——**选用的行为是模型原生的，工具能力来自预装脚手架**。

**边界（诚实声明）**：
- 能力"还可以" ≠ 稳定：同为许愿式生成，最差 T3 全透明、BB 渲染残留——**方差大**；
- 评级为单用户实机主观判断，非自动化评测；
- 工程脚手架（指令层：验证指令/质量门槛/验收清单）仍显著提高下限：PA 黑屏（验证绕开真实启动路径）、B2 半格错位、B+T 草方向、RL 方向解算均属"验证对象/粒度/角度"缺口（见 5.6/5.7/8 节）——许愿式生成暴露的是**模型原生验证盲区**，不是工程能力上限。

### 0.5 结论边界、不严谨之处与免责声明

**能得出的结论（唯一可外推为"能力可用"）**：模型在"指令层无工程脚手架 + 环境层能力脚手架"的许愿式生成下，**原生工程能力已可用**——11/11 交付可运行产物、6/11 评级中等以上、自研与 three.js 两条技术路线完整走通。

**微观语言特征不构成能力检测**：let me / I'll / I'm doing / I'm going to / we need / we should 等词形与情态语言特征，在本测试样例下**检测不出能力高低**（I 型之王 B1 与 we 型之王 UP 同样最好；情态三高 UP/BB/B3 质量好/差/中皆有）——第 5 节全部词频/短语/情态/句首统计均为**描述性观察**（描述轨迹形态），不预测、不检测能力，亦不能用于其他场景的能力判断。

**外推边界**：本测试是**单一任务（许愿式生成：Minecraft 复刻）× 单一模型（DeepSeek V4 Pro max）× 单一环境**的样例，**不代表其他任何任务、任何场景、任何配置下的能力**。

**测试不严谨之处（已知）**：
- **Full access 权限开启时机不一致**：部分会话一开头即开启 Full access，部分会话执行到中途某一步后才开启——权限状态影响工具执行（bash / playwright / 文件写入）能力，属实验控制不一致；
- **n=1，未重复跑**：每个配置只跑一个会话，无重复实验、无统计显著性；
- 评级为单用户实机主观判断。

**免责声明**：以上所有结论均基于本组参考数据归纳，**仅供参考，不保证可复现，结论不保证为真**。

## 1. 十一会话启动说明（每个会话第一轮/第二轮分别发生了什么）

十一个会话任务相同，区别只在开头：**第一轮给模型几个工具、有没有输出上限、有没有额外注入一段"说话风格"要求**。

### B1（旧版 anchored-standard）
- **第一轮**：只给 2 个工具（pwsh、read），并且这一轮最多只能输出 1024 token（约一小段规划）。没有注入任何额外内容。模型收到任务后先做了一轮简短规划。
- **第二轮**（用户发"继续"后）：61 个工具全部开放，输出不再受限，正常干活。

### UP（upstream main 形态）
- **第一轮**：只给 2 个工具（bash——Git Bash on Windows 的 custom-bash 工具、str_replace_editor 文件编辑器），输出不限制。
- **第二轮**：61 个工具全部开放。（此形态注入比旧版少：工具是"常用小集合 + 按需解锁"，不是一次全给）

### B2（回退后修复版）
- **第一轮**：只给 2 个工具（pwsh、read），输出不限制。
- **第二轮**：61 个工具全部开放。

### B3（与 B2 完全相同）
- **第一轮**：同 B2（pwsh、read）。模型这一轮纯思考了很久（约 5 分钟没动手），被用户中止。
- **第二轮**（用户发"继续"后）：61 个工具全开，22 分钟完成交付。

### T1（注入"不要用 let me"的说话风格要求）
- **第一轮**：0 个工具。注入一条消息，内容是"不要用 'let me' 开头，改用 'I'll' 或 'I'"。模型只回复了一句确认。
- **第二轮**：61 个工具全开。**要求没生效**——模型第二轮起照样用了 135 次 let me。

### T2（注入"只用 we"的说话风格要求）
- **第一轮**：0 个工具。注入的消息是"只用 we/let's/our，禁用 I/let me/my，每段分析用 'We need' 开头"。模型回复确认。
- **第二轮**：61 个工具全开。**要求生效**——let me 只用了 15 次，we 用了 242 次。

### T3（同样的要求，但写进系统提示）
- **第一轮**：没有特殊处理，任务进来直接 61 个工具全开。同样的"只用 we"要求这次是写进系统提示里的，不是注入消息。
- **结果**：要求没生效（let me 161 次）——同样的话，作为消息注入有效，写进系统提示无效。

### B+T（禁 let me 要求 + 模板）
- **第一轮**：同 T1（0 个工具 + 禁 let me 要求）。
- **第二轮**：61 个工具全开，要求生效了一阵（let me 只用了 45 次）；中途中断 4 小时，用户"继续"后第三轮 let me 又爆到 212 次——**说话风格要求随时间衰减**。

### PA（标准模式 + 用户自带提示词）
- **第一轮**：没有特殊处理，61 个工具直接全开。唯一特别的是用户的任务消息自带一份"首块规划提示词"（先勘察目录、列出交付物、定功能清单、思考节奏、技术选型、验证方案、收尾框架）。
- **之后**：正常干活（80 块推理，零依赖自研 88KB + 26 个单元测试）。

### BB（Git Bash 版）
- **第一轮**：只给 2 个工具（bash、read）——新预设把 pwsh 换成了 Git Bash。
- **第二轮**：61 个工具全开。因为 Git Bash 输出的路径是 /d/... 格式、而文件工具按 Windows 的 D:\... 解析，模型把项目写到了 D:\d\code（目录事故，会话末尾才 git clone 迁回）。

### RL（anchored-standard-open 首跑）
- **第一轮**：只给 2 个工具（bash、str_replace_editor），系统提示一句 "You are a helpful software engineer assistant."，无注入、无输出上限——与官方 minimal RL 接口逐字节一致。模型只做了 1 次 bash 探测。
- **第二轮**（第一个工具调用后自动晋升，无需用户介入）：63 个工具全部开放，skill 目录注入恢复。step 3 立即产出 65k 字符的完整架构设计，此后全程无路径事故（Git Bash 路径约定修复版生效）。

## 4. 宏观结论：质量决定因素

> 以下三条为本组 11 样本的**归纳性观察**，非因果结论，受 0.5 节不严谨之处与免责声明约束。

1. **首块规划深度** → 技术路线与功能面（B1/UP 深规划 → 自研/完整；B2 浅规划 → 功能缩水）
2. **验证粒度 ≥ 缺陷粒度** → 正确性（B1 像素级/UP 画面级 vs 其余颜色/状态级）
3. **思考-行动交替** → 完成度（所有闭合思考后必行动；未闭合发散是唯一失败形态）
4. **工具面持续时间决定轨迹形态**（RL 新证据）：首轮锚定只作用于首轮——RL 晋升即 63 工具全开，轨迹立即回归 standard 系（we 1.74 / let me 0.26 中间带）；旧 anchored 全程小工具面才保持全程 minimal 轨迹。**"轨迹锚定"是工具面约束的持续效应，不是 schema 的一次性效应**。
5. **验证角度必须覆盖一般情形**（RL 新证据）：方向解算的推导与实测都只在 yaw=0 退化点自洽——**退化点验证闭合**盲区（与 BB flipY"框架默认值盲区"并列），用户实机按键方向错误。

- **UP/BB/B3 情态三高**（合计 4.66/3.85/3.65/1k），且 **B3 与 UP 基本同档**：could 143 vs 146 次、can 117 vs 132 次、need 58 vs 74 次、should 62 vs 49 次（B3 反而更高）——"UP 情态垄断"的说法不成立
- 情态合计前四（UP 4.66 / BB 3.85 / B3 3.65 / T2 2.59）恰好也是 we 家族密度前四（3.32 / 3.44 / 2.63 / 2.96）——**情态丰富与 we 型代词家族绑定**（"we need X / we can Y / could be Z" 是同一套规划语言的两个侧面）
- **但情态高不预测质量**：三高会话中 UP 最好、B3 较好（仍有边角碰撞）、BB 有渲染问题；而最好的 B1 情态合计最低（1.36），PA（还行）也最低（1.12）——好坏两极都出现在高、低两端，**情态密度与质量脱钩**
- 单 Context 口径下 T3 情态不再贫乏（need 0.19 / could 0.33 / can 0.42，全为中位）——旧"T3 情态贫乏"结论是链路累积分母（reasoning 长的会话被稀释）的产物
- B+T 的 should 高（0.72）但 be 化（should be 占多数——描述性而非行动性）
- PA 的 must 全会话最高（0.16）——"must"规范性要求（提示词"必须建立验证手段"的直接体现）
- **RL 情态合计 2.10 落中位**（need 0.14 / could 0.68 / can 0.66——need 低、could/can 中高）：与 we 家族中间带（1.74）一致，**情态密度跟随轨迹带而非质量**（RL 较好、B1 最好但情态最低）

**should 后的动词分好坏**：

| 会话 | should + 动词 Top | 性质 |
| --- | --- | --- |
| **B1** | be:31, have:5, show:4, produce:2, plan, check, initialize | 规划+执行 |
| **UP** | be:7, use:5, map:3, show:3, consider:2, persist | 技术规范（"should map to v = 1 - tileY/16"） |
| B2 | be:23, show:8, build:2, proceed, create | 选型后执行 |
| B3 | be:16, work:6, run:3, check, render | 中间态 |
| T1 | be:11, hit:4, ask, acknowledge, check | I-should=13（唯一高） |
| **T3** | be:16, work:5, show:2 | **"should work"（验收假设，非验证）** |
| **B+T** | be:46（1/3 是 "should be" 描述性）, check:4 少 | 描述为主 |
| **PA** | be:24, work:6 | be 化但 check=150 实际驱动 |

- T3 的 should + work:5："should work; Playwright connects..."——把"应该能跑"当验收标准
- B1 的 should + check/plan/produce——把"应该"导向行动
- 主语：I-should 最高是 T1（13，I 系要求），we-should 最高是 BB=18 / UP=13 / T2=10（we 系要求）——与代词家族一致

**need 的搭配**：
- UP：we need + ensure:5/create:3/test:3/inspect:2——"we need ensure..."（省略 to 的祈使需求）
- B1：need to + build/create/check/verify + need-N（neighbor/per/actual/ensure）——"need to verify/check" 验证导向
- T3：need to + be/call/change——最少最弱

### 5.6 微观结论

> 好会话思维链 = 高频 `potential`（预判）或 `test`（验证）+ 执行/验证动词；差会话 = 发散动词（also/think/just）+ should work 假设验收。**情态密度与质量脱钩**（是 we 型轨迹的语言特征，B3/BB 情态三高但质量中/差、B1 最低却最好）；词形（I/we）无关，**词后动词**相关。

1. **potential（预判）是 UP 的无 bug 指纹**：动手前先枚举潜在问题
2. **test/check + 具体现象是 B1 的无 bug 指纹**：验证时报告"看见了什么"，而非"通过"
3. **代词本身无关，代词后的动词才相关**：好会话 = 执行/验证动词（check/test/write/verify/run/patch/fix），差会话混入发散动词（also/think/just/maybe）
4. **fine/maybe 不是信号**（密度不区分好坏），hmm、let me also、let me think、let me just 是弱负信号
5. **光有 potential 词不够**：B2 也写过 "Potential issues to watch"（12 次），但词后没有跟排查动作——**词必须驱动行动**（与宏观"思考闭合"结论一致）

**各会话微观定位**：

- **B+T（中等）**：letMe 密度全会话最高（1.33/1k，261 次——B 要求+模板在 turn2 曾压到 45，turn3 继续后爆到 212，**约束长会话衰减**）、potential 最低（2 次）、should 最高但 be 化（be:46/137）。微观属差会话家族，但交付"中等"——check/test/verify 验证量充足（146/110/39）补偿了下限，验证粒度（漏"纹理方向"）限制了上限。
- **PA（黑屏已修）**：test/check/verify/fix 四高（1.38/0.54/0.24/0.27——10 会话最高档，**提示词【验证方案】的 TDD 化执行**）+ must 最高（0.16）+ letMe 0.80（I 系推进）+ potential 缺失（3 次，提示词未含"预判"）。微观属"验证-修复驱动"型——but/actually/hmm 句首高（自我纠正频繁），但**黑屏漏网证明验证量再大也救不了"验证对象 ≠ 真实运行路径"**；用户修复后评级"还行"。
- **BB（不行：目录+渲染问题）**：**letMe=6 / we 家族 566 / we should=18（三项全会话最优档）**——Git Bash 首轮锚定的 we 型轨迹比 UP 更"纯"，但**轨迹纯度与渲染 bug 数无关**（flipY 全黑 + 用户实机的区块/破坏残留问题）。**预判修正**：potential=21（0.13/1k tok，除 UP 外最高，与 B3 并列）+ could=215（1.31，全会话第二）——预判密度第二高，预判的全是**已知风险点**（AO/碰撞/性能/指针锁定/透明排序），flipY 是**框架默认值类 bug（CanvasTexture flipY=true）不在预判清单**，靠 40+ 块像素级排查定位——**诊断强（材质替换隔离链、"That's it!"顿悟）但"未知 API 默认值"类风险无预判手段**。加上目录事故（MSYS/Windows 双路径，20+ 块推理消耗），BB 是"工具约定缺失 + 轨迹完美 + 预判盲区（框架默认值）"三因素叠加的对照样本。
- **RL（较好：anchored-standard-open 首跑）**：**轨迹中间带**（we 1.74 / let me 0.26——介于 anchored 带 2.6–3.4 与 standard 带 0.5–0.9 之间）+ **验收确认型语言**（fine 1.31 全会话次数第一、hmm 0.07 最低档、句首 Good/Fine）——"快速检查、频繁确认、很少悬置"。**let's 搭配 100% 执行类**（check/test/do/add/write）。potential 0.14（与 BB/B3 并列第二档）——预判了已知风险点，但**方向解算 bug 是"退化点验证闭合"盲区**：step 11 数学推导与 step 86 实测验证都只在 yaw=0 特例自洽（sin0=0 消掉交叉项误差），非零 yaw 的旋转顺序/符号从未被覆盖——**验证粒度细（像素/物理/控制台）但验证角度单一（默认朝向）**，与 BB flipY"框架默认值盲区"并列第二个盲区模式。水是唯一系统性设计+显式实现（游泳浮力）+持续验证的功能，用户实测可游泳、未报水渲染问题。

### 5.7 对提示词工程的启示（微观脚手架）

在 standard-first-block-prompt 基础上可追加（可选）：
- 每个 `let me / let's / we can` 之后必须跟执行动词（check/test/write/verify/run/fix/patch/define）
- 禁止悬置句式：`let me also`、`let me think about`、`let me just`
- 每个里程碑先写一行 "Potential issue: ..." 枚举，再逐个验证
- 验证报告格式："我采样/断言了什么 → 观察到什么 → 对不对"（现象优先，不用"fine/ok"收尾）
- **方向/旋转/坐标类计算必须验证一般角度**（RL 教训）：除默认朝向（yaw=0）外，至少再断言 yaw=90°/180° 的期望位置——退化点自洽 ≠ 一般情形正确
- 涉及"框架默认行为"的代码（纹理 flipY/mipmap、旋转矩阵更新）在实现时写自检行（BB 的 flipY 教训）

## 6. 实验变量全部证伪

风格要求（T2 生效却贴图错）、1024 cap（B1 有/UP 无都好）、工具屏蔽（UP 受限仍交付）、词形（I/we 两极都好）——**无一预测质量**。质量在思维链深层结构，不在注入表面。

**新增变量（BB）**：**shell 类型（Git Bash vs pwsh）与锚定工具对（[bash,read] vs [pwsh,read]）也不预测质量**——轨迹完全复现（letMe=0、we 型），但渲染问题照旧。**新引入的变量是负资产**：MSYS/Windows 双路径直接造成目录事故（custom-bash 缺路径约定）。工具输出格式与文件工具的兼容性，成为继注入/契约/cap 之后的第四个"表面变量"。

**新增变量（RL）**：**首轮接口严格官方 minimal（[bash, str_replace_editor] + 一句 persona + 零注入）+ 晋升后全开**——机制全部按设计工作（request/header 实测逐字节一致、无 resident 隐藏组件、无路径事故），但**"首轮锚定"只产生微弱轨迹残留**（we 1.74 / let me 0.26 中间带），评级较好。**修正：轨迹锚定不是 schema 的一次性效应，而是工具面约束的持续效应**——旧 anchored 全程小工具面 → 全程 minimal 轨迹；RL 晋升即 63 工具全开 → 轨迹立即回归 standard 系。首轮接口纯净性、晋升全开、轨迹形态三者解耦：接口纯净 ✓（request 实测）、晋升全开 ✓（63 工具）、轨迹锚定仅首轮（设计使然）。

## 8. 对下一轮实验的建议

1. **验证指令注入**（比风格指令值钱）：要求像素级/几何级断言（B1/UP 已证明有效）
2. **微观脚手架**：代词后必须跟执行动词；禁 let me also/think/just；每里程碑先枚举 Potential issue
3. **思考节奏**：长思考合法但必须闭合为动作；未闭合 = 被中止风险
4. **渲染质量验证补课**：mipmap 混色、半格错位、全透明均漏过现有验证——验证清单需含"纹理 tile 正确性 + 几何对齐"断言
5. **自定义 shell 工具必须显式约定路径格式**（BB 教训）：工具描述写死"文件工具只收 Windows 路径、bash 输出 MSYS 路径、转换表如下"，并在 execute 层兜底转换 workdir——否则模型会把 bash 输出路径直传文件工具造成目录错位
6. **纹理约定自检**（BB 的 flipY 教训）：涉及纹理/UV 的代码应在实现时写"UV 坐标约定 + flipY/mipmap 设置"的自检行，而非依赖事后像素排查
7. **交互/方向类验证补课**（RL 教训）：方向、旋转、输入映射类代码必须验证**一般角度**（至少 yaw=0/90/180 三点断言期望位置），默认朝向自洽 ≠ 一般情形正确
8. **anchored-standard-open 验证结论**：若目标是"严格官方 RL 接口开局 + 之后全开"，本预设达成且无缺陷（首轮 request 逐字节一致、晋升全开、无路径事故）；**若目标是全程 minimal 轨迹（modeltest 96-99 带），必须保持小工具面不扩大**——轨迹锚定是工具面持续约束的效应，不是一次晋升能锁定的
