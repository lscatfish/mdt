### 0.3 密度统计口径

- **交付链路**：任务消息（含"继续"恢复轮）至模型"通知完成"的最终总结；交付后的追问轮排除。

### 0.4 实验性质说明：许愿式生成

**任务提示词原文**（十二会话完全一致，一条用户消息）：

> 你只能够修改当前目录下的文件，可以使用 git 进行版本管理。请复刻一个网页版本的我的世界游戏

（各预设的系统提示与注入差异见第 1 节；会话还含一条 harness 环境消息"approval policy changed from ask to never"，非任务内容。）

**什么是"许愿式生成"**：本次实验的统一性质定义——**指令层**没有工程脚手架：任务提示词只提出愿望式目标（"复刻一个网页版本的我的世界"），无验证指令、无质量标准、无技术选型约束、无验收清单、无工程规范注入。模型拿到的是"目标 + 当前目录 + git 权限"，技术路线、功能面、验证方案全部由模型自主决定。

**但环境层自带能力脚手架（用户预装，非实验变量）**：
- **4 个 MCP 服务器**（晋升后全部进入工具目录，共 36 个工具）：playwright（浏览器自动化，24 工具）、server-memory（会话记忆知识图谱，9）、context7（库文档查询，2）、codegraph（代码检索，1）；
- **项目 skill 目录注入（Matt Pocock 的 skills 集）**：用户安装的 Matt Pocock skills。**该注入是普遍机制，所有会话在工具面全开/晋升后都会出现**，并非 RL 特有——anchored 系预设首轮剥离 skill-catalog、晋升后恢复；zero-anchored 系第二轮注入（try 会话实测 turn2 工具目录含 skill-catalog）；standard 系全开即注入。RL-open 会话是**唯一做过 request/header 逐字节实测**的，确认注入 15 项（code-review / tdd / grilling / diagnosing-bugs / prototype / research / wizard / writing-for-agents 等），具体数量随项目目录的 skill 目录而异；
- 因此"许愿式生成"的准确含义是：**指令层零工程要求，环境层脚手架齐备**。验证文化的工具基础正是这个脚手架——playwright 使像素断言/控制台检查成为可能；模型的自主性体现在**在无任何提示下选择使用**（RL 调用 playwright 74 次，codegraph/context7/server-memory/skill 0 次——脚手架可用，用不用、怎么用由模型决定）。anchored 系预设首轮只暴露 2 个工具（MCP 不可见），晋升后才可见可用。

**它的规划性质：短程规划，不是长程规划**。生成过程确实带有规划，但形态是：
- **前期一次性架构设计**（如 RL step 3 的 65k 字符设计块、B1/UP 的深首块）——把功能面/文件结构/技术路线一次性定下来，之后进入执行；
- **逐块"思考-行动"交替的局部决策**——每个推理块闭合后立即调用工具，决策窗口只有"下一两个动作"（宏观结论第 3 条：完成度来自逐块闭合，不来自全局计划）；
- **没有长程规划**：无计划状态维护（todo_write 极少且不持续）、无里程碑跟踪、无跨阶段约束保持（B+T 中断 4 小时后恢复时风格要求未保持——约束没有跨中断持久化；注意全部会话 Context <300k、B+T 仅 197k，属小任务规模，**并非长会话**；RL 执行中大量涌现式局部调整——出生点水下、游泳浮力等 step 61–74 均为执行时的新决策）。
- 一句话：**愿望式目标 → 一次性设计 → 短程逐块执行**，全程没有"长期计划"这个状态被维护。

**我们没有做什么**：没有针对"工程能力"设计对照实验——全部干预变量都是表达层/工具面变量（说话风格要求、锚定工具对、输出 cap、注入方式），没有一个是工程能力类干预。因此本报告结论应被读作：**模型在"指令层无工程脚手架、环境层有 MCP/Skill 能力脚手架"下的原生工程能力表现**。

**工程能力评价：还是可以的**：
- **12/12 会话都交付了可运行产物**（git 提交 + 本地启动可玩），无一中途放弃或不可启动；
- **8/12 得分 ≥60（细则打分制，见 2.3）**：好档 ≥80 = B1/UP/T1/B3（4 个）；中档 60–79 = B2/RL/B+T/PA（4 个）；差档 <60 = T2/UP2/T3/BB（4 个）；
- **两条技术路线都完整走通**：零依赖自研（B1 90KB 自研渲染、PA 88KB + 26 单元测试）与 three.js 模块化（7–8 文件：噪声/世界/网格/玩家/游戏/方块）均实现完整功能面（程序化地形、区块流式、AABB 碰撞、方块交互、昼夜循环、存档）；
- **验证行为原生具备（工具来自脚手架）**：在 playwright MCP 可用下，playwright 自动化验证普遍出现（像素断言、控制台零错误、物理模拟），多数会话在无任何提示下自主完成验证——**选用的行为是模型原生的，工具能力来自预装脚手架**。

**边界（诚实声明）**：
- 能力"还可以" ≠ 稳定：同为许愿式生成，最差 T3 全透明、BB 渲染残留——**方差大**；
- 评级为单用户实机主观判断，非自动化评测；
- 工程脚手架（指令层：验证指令/质量门槛/验收清单）仍显著提高下限：PA 黑屏（验证绕开真实启动路径）、B2 半格错位、B+T 草方向、RL 方向解算均属"验证对象/粒度/角度"缺口（见 5.6/5.7/8 节）——许愿式生成暴露的是**模型原生验证盲区**，不是工程能力上限。

### 0.5 结论边界、不严谨之处与免责声明

**能得出的结论（唯一可外推为"能力可用"）**：模型在"指令层无工程脚手架 + 环境层能力脚手架"的许愿式生成下，**原生工程能力已可用**——12/12 交付可运行产物、8/12 打分 ≥60（细则打分制，见 2.3）、自研与 three.js 两条技术路线完整走通。

**微观语言特征不构成能力检测**：let me / I'll / I'm doing / I'm going to / we need / we should 等词形与情态语言特征，在本测试样例下**检测不出能力高低**（I 型之王 B1 与 we 型之王 UP 同样最好；情态三高 UP/BB/B3 质量为 85.7 / 5.0 / 80.0，好/差/好档皆有）——第 5 节全部词频/短语/情态/句首统计均为**描述性观察**（描述轨迹形态），不预测、不检测能力，亦不能用于其他场景的能力判断。

**外推边界**：本测试是**单一任务（许愿式生成：Minecraft 复刻）× 单一模型（DeepSeek V4 Pro max）× 单一环境**的样例，**不代表其他任何任务、任何场景、任何配置下的能力**。

**测试不严谨之处（已知）**：
- **Full access 权限开启时机不一致**：部分会话一开头即开启 Full access，部分会话执行到中途某一步后才开启——权限状态影响工具执行（bash / playwright / 文件写入）能力，属实验控制不一致；
- **n=1，未重复跑**：每个配置只跑一个会话，无重复实验、无统计显著性；
- 评级为单用户实机主观判断。

**三个变量的可证明边界（2026-08-16 全量回测 + UP2 复测后明确）**：
- **锚定（首轮窄工具面）**：只能引证"与好结果正向共现倾向"（细则打分制好档 ≥80 在锚定组 3/4 vs 非锚定组 1/4，见 2.3）；**不能证明充分提升**——BB（同锚定、轨迹最纯）5.0、B2（同预设）71.1、UP2（同形态复测）27.8、锚定组无配对对照（7 会话 6 种预设形态，无法分离锚定与预设贡献）。
- **思维链**：**内容属性**（首块规划深度、验证粒度/对象/角度、思考闭合）与质量共现；**形态属性**（长度/努力量/词形）与质量脱钩（UP 最短 92k 好档、PA 最长 253k 黑屏；BB 诊断链最强最差）。相关≠因果，且 BB/PA 反例排除"充分提升"。
- **提示词注入**：能可靠改变**行为/轨迹**（T2 契约生效、PA 提示词 1:1 执行、锚点消息 > system prompt）；**不是质量开关**（T2 风格最纯贴图照错、PA 指令全执行黑屏照旧、B1 无注入最好）——"即使 let me 消失也存在问题"。

**免责声明**：以上所有结论均基于本组参考数据归纳，**仅供参考，不保证可复现，结论不保证为真**。

### 0.6 常见疑问查证（事实核验）

对讨论中反复出现、容易被记混的几个事实做集中核验（全部对应本报告数据；modeltest 侧结论见第 7 节引用声明）。

**Q1：let me 频繁出现的会话里，有结果好的吗？**
- 有，两个：**B1**（letMe=128，0.65/1k，全会话第二高）打分 86.8（好档）；**PA**（letMe=203，0.80）用了全套流程强约束提示词（勘察/交付物/功能/思考节奏/选型/验证/收尾框架），启动黑屏是它唯一严重 bug（渲染循环未启动，一行修复），修复后打分 60.5（中档）。
- 对照：高 letMe 但低分的有 T1（135，80.6）、T3（156，18.8）、B+T（261，68.4）。**同一指标区间内高低分皆有——轨迹与结果好坏的关系不明显**。

**Q2：RL（首轮 minimal 锚定 + 晋升后 63 工具全开）的效果到底如何？**
- **打分 71.1（中档，与 B2 同分）**，不是"不好"。用户实测原话："效果较好（与 B3 同档）"——该"同档"为主观评级表述；细则打分制下 RL 71.1 中档、B3 80.0 好档，**已不同档**（B3 因模式默认创造加分升档）。操作键的按键方向解算有问题；可以游泳；未报水渲染问题。容易与 T3（18.8）/BB（5.0）记混——区分依据：RL 无启动/渲染级 bug，问题集中在按键方向解算单点。

**Q3：轨迹、锚定、结果三者到底是什么关系？**
- **轨迹与结果基本脱钩**：BB 轨迹最纯（letMe=6、we 家族 566）打分 5.0；B1 轨迹最散（letMe=128）打分 86.8。轨迹是表达层形态（由工具面/注入决定），不编码结果好坏。
- **锚定与结果有正向倾向但非充分**：好档（≥80）锚定组 3 个（B1/UP/B3）+ 非锚定组 1 个（T1 80.6）；但 BB 同锚定却 5.0 分。同条件内也有抽卡成分：B2/B3 同为修复版 anchored，71.1 vs 80.0。
- **好结果仍可能用 let me 输出**：B1 = 86.8 分 + 全会话第二高 letMe。

**Q4：potential 是不是最重要的指标？**
- 它是**跨任务最一致的指纹**：UP 134 次（1.46/1k，句首 126 次专属）；modeltest 侧句首 potential 只出现在 96–99 分的 minimal/anchored 样本，跨任务同向（第 7 节）。
- 但有两条边界：① **B1 最好却 potential 极低**（11 次，0.06）——potential 是"upstream 形态"的指纹（UP/UP2 均 ~1.4-1.5），不是"好会话"的指纹；② **B2 也写过 "Potential issues to watch"（12 次）但词后没有排查动作**——光有词不够，词必须驱动行动（与宏观"思考闭合"结论一致）；③ **UP2 同形态复测 potential 164 次（1.41）与 UP 持平，但 27.8 分差档**——预判密度不预测质量。

**Q5：5.2 节"合计密度"为什么有的值超过 1？**
- 单位是**次 / 1k tokens**（口径见 0.3），是计数密度、不是比例/概率，没有上界。B+T 的 let me=1.33 表示"每 1,000 token 出现 1.33 次"（261 次 ÷ 197k Context）；"家族合计"是各明细密度相加（I 家族 = let me + I + I'll + I should + I'm + I've + I'd），B+T 的 I 家族合计 2.44、BB 的 we 家族合计 3.44 均属正常标度，不是错误。

**Q6：基于本实验能不能做数学显著性推导？**
- **不能。** 每条件 n=1（组内方差无法估计）、非随机分配、评级为主观序数、混杂变量多（中断、Full access 时机、平台差异）。当前只能给出两层弱证据：描述性效应量（如 letMe 128 vs 2）与跨数据集方向复现（modeltest 与本实验在 potential/let_me 分带上同向）——属"证据累积"，不是"显著性证明"。若未来要显著性：n≥3/条件、同一任务同一平台、盲评、置换检验（permutation test）；即便如此，评级主观性仍是天花板。

## 1. 十二会话启动说明（每个会话第一轮/第二轮分别发生了什么）

十二个会话任务相同，区别只在开头：**第一轮给模型几个工具、有没有输出上限、有没有额外注入一段"说话风格"要求**。

### B1（旧版 anchored-standard）
- **第一轮**：只给 2 个工具（pwsh、read），并且这一轮最多只能输出 1024 token（约一小段规划）。没有注入任何额外内容。模型收到任务后先做了一轮简短规划。
- **第二轮**（用户发"继续"后）：61 个工具全部开放，输出不再受限，正常干活。

### UP（upstream main 形态）
- **第一轮**：只给 2 个工具（bash——Git Bash on Windows 的 custom-bash 工具、str_replace_editor 文件编辑器），输出不限制。
- **第二轮**：61 个工具全部开放。（此形态注入比旧版少：工具是"常用小集合 + 按需解锁"，不是一次全给）

### UP2（UP 的同形态复测，baseline-upstream2）
- **第一轮**：与 UP 完全相同——bash + str_replace_editor（Git Bash）。

### T1（注入"不要用 let me"的说话风格要求）

> **契约定义（全文统一，后面不再重复）**：本报告的"契约"指注入给模型的**说话风格要求**，有两个版本：
> - **A 契约（we 型正向引导）**，原文："只用 we/let's/our，禁用 I/let me/my，每段分析用 'We need' 开头"；
> - **B 契约（禁 let me 型）**，原文："不要用 'let me' 开头，改用 'I'll' 或 'I'"。
> 注入方式有两种：**anchor 消息**（首轮 0 工具锚点轮，作为一条用户消息注入）或 **system prompt**（写入系统提示 -200 section）。第 3 节契约列用 `A-anchor` / `B-anchor` / `A-std`（std = system prompt）/ `B-anchor+模板` 表示版本×注入方式的组合；"模板"= 额外的交付流程模板（B+T 会话）。
> 
> - **第一轮**：0 个工具。注入一条消息，内容是"不要用 'let me' 开头，改用 'I'll' 或 'I'"（即 B 契约）。模型只回复了一句确认。

## 4. 宏观观察：与质量共现的因素（非因果）

> 以下为本组 12 样本的**描述性共现观察**，非因果结论、非充分条件证明——每个因素都存在反例（见下），受 0.5 节不严谨之处与免责声明约束。**本节与第 6 节共同构成"两轴独立"论证：表达层变量（轨迹/语言/行为）可被工具面与提示词可靠改变，但质量由工程层（首块规划深度、验证粒度/对象/角度）决定，两轴之间无充分传导。**

1. **首块规划深度与质量共现**：B1/UP 深规划 → 自研/完整；B2 浅规划 → 功能缩水（描述性：B1 首块 4,250 chars vs B2 425 chars；但深度与质量无配对对照，不能证明因果）
2. **验证粒度 ≥ 缺陷粒度与正确性共现**：B1 像素级/UP 画面级 vs 其余颜色/状态级（反例：PA 验证量最大（test=349）仍黑屏——验证对象 ≠ 真实运行路径，故"验证多"不等于"验证对"）
3. **思考-行动交替与完成度共现**：多数闭合思考后必行动；未闭合发散是被中止的形态（B3 首轮未闭合被中止后"继续"仍完成交付——未闭合不是必然失败，只是被中止风险）
4. **工具面持续时间决定轨迹形态**（RL 新证据）：首轮锚定只作用于首轮——RL 晋升即 63 工具全开，轨迹立即回归 standard 系（we 1.74 / let me 0.26 中间带）；旧 anchored 全程小工具面才保持全程 minimal 轨迹。**"轨迹锚定"是工具面约束的持续效应，不是 schema 的一次性效应**（这是轨迹层面的结论，与质量无关）。
5. **验证角度必须覆盖一般情形**（RL 新证据）：方向解算的推导与实测都只在 yaw=0 退化点自洽——**退化点验证闭合**盲区（与 BB flipY"框架默认值盲区"并列），用户实机按键方向错误。
6. **锚定与质量：正向倾向，非充分**（见 0.5/第 6 节）：细则打分制下，好档（≥80）**3/4 在锚定组**（B1 86.8/UP 85.7/B3 80.0 vs 非锚定组 T1 80.6——T1 升入好档后"全部在锚定组"不再成立），差档（<60）锚定/非锚定各半（T2 35.7/T3 18.8 vs BB 5.0/UP2 27.8）；但 BB（同锚定、轨迹最纯）5.0、UP2（与 UP 同形态同轨迹）27.8、B2（同预设修复版）71.1 低于非锚定的 T1 80.6——**有正向共现倾向，存在双向反例，不能证明锚定提升质量**。

- UP/UP2/B2/B3/T2/BB 为 we 型（we 家族 0.86-4.31）；T1/T3/B+T/PA/B1 为 I 型（I 家族 1.29-2.44）——**但两极最好的会话（B1、UP）风格完全相反，代词本身不预测质量**

**发现 5：should 的主语跟随代词家族**
- we should 集中在 we 型会话（UP=0.14、UP2=0.08、BB=0.11、T2=0.06）；I should 集中在 I 型（T1=0.08、B+T=0.05、B1=0.04、PA=0.02）

### 5.6 微观结论

> **地位声明（修正）**：以下全部为**描述性观察**，是"哪些语言形态在好/差会话中出现了"的记录，**不是能力检测手段，更不能外推为"改变语言 = 提升质量"**——本节的每个"指纹"都存在反例（BB 轨迹最纯最差、B1 无 potential 最好、PA 验证量最大仍黑屏），**语言形态与质量两轴独立**（第 4/6 节）。任何把微观特征当"脚手架"使用的建议（5.7）均未做配对对照验证，效果未知。

#### 5.6.0 UP vs UP2 同形态指纹对比（第一次独立复现）

**结论（5.6.0）**：

1. **形态指纹可复现**：letMe=2、potential≈1.4 句首预判、we 型 3.3–4.3、I 型 <0.1、hmm 最低档、maybe 最高档探索型、情态合计 4.7–5.1、句首族——**UP/UP2 两次独立运行全部一致或同档**。此前所有"指纹"都是 n=1 单会话观察（且混有预设差异），UP2 提供了第一次干净复现：**这些是 upstream 形态→轨迹的可靠映射**（表达层内可复现）。
2. **质量不可复现**：同形态、同轨迹（letMe 均 2、potential 均 1.4、we 型同带），质量 85.7 vs 27.8（渲染超级大故障）——**"形态指纹可复现 ≠ 质量可复现"，是两轴独立（第 6 节）最干净的一次对照**（比 BB 强：BB 还混有目录事故，UP2 无任何混杂因素）。
3. **potential 指纹定性与修正**：UP 单会话时被记为"UP 型好会话指纹"；UP2 复测后修正为"**upstream 形态指纹**"——形态可复现（两次均 ~1.4-1.5），**质量指纹不成立**（UP2 同密度 27.8 分）。同时验证用法一致性：预判枚举（句首）是 upstream 形态的语言习惯，但"预判了"不等于"修对了"（UP2 预判密度与 UP 持平，渲染仍大故障）。
4. **验证量与验证对象**：UP2 验证并不少（85 次工具调用中 40+ 为浏览器实测/像素断言），仍渲染大故障——与 PA（test=349 黑屏）共同说明**验证量不预测质量，验证对象/粒度/角度才相关**（第 4 节第 2 条）。
5. **水关注度弱线索**：UP2 思维链 water 262 次（2.26/1k，UP 162 次 1.76），对应用户实测 UP2 水系统全会话最完整（挖不掉+可填充+进水特效+游泳）——但 B1 water 356 次（最多）水仍可破坏，**关注度与功能质量无单调关系，仅记录不引证**。

**逐项微观观察（11 会话基础，5.6.0 之外）**：

1. **test/check + 具体现象是 B1 型会话的伴随特征**：B1 验证时报告"看见了什么"（black=104/null=74）——验证思维是"**我看见什么、对不对**"（"t0→BLACK、t1→BLACK"），不是抽象的"测试通过"；PA test 最多（349）仍黑屏——**验证量不预测质量，验证对象/粒度才相关**（5.6.0 结论 4 补充）
2. **代词本身无关，代词后的动词才相关（描述性）**：好会话 = 执行/验证动词（check/test/write/verify/run/patch/fix），差会话混入发散动词（also/think/just/maybe）；B1/UP/UP2/RL 的 let me/let's 搭配全执行类（或几乎不用），T3/B+T 混入发散
3. **fine/maybe 不是信号**（密度不区分好坏——UP/UP2 的 maybe/fine 全会话最高档但质量两极），hmm、let me also、let me think、let me just 是弱负信号（描述性，非检测）
4. **光有 potential 词不够**：B2 也写过 "Potential issues to watch"（12 次），但词后没有跟排查动作；UP2 预判密度与 UP 持平仍渲染大故障——**词必须驱动行动**（与宏观"思考闭合"观察一致）

**各会话微观定位**：

- **B+T（中等）**：letMe 密度全会话最高（1.33/1k，261 次——B 要求+模板在 turn2 曾压到 45，turn3 继续后爆到 212，**约束未跨中断保持**；Context 197k 属小任务规模，并非长会话）、potential 最低（2 次）、should 最高但 be 化（be:46/137）。微观属差会话家族，但交付"中等"——check/test/verify 验证量充足（146/110/39）补偿了下限，验证粒度（漏"纹理方向"）限制了上限。
- **PA（黑屏已修）**：test/check/verify/fix 四高（1.38/0.54/0.24/0.27——12 会话最高档，**提示词【验证方案】的 TDD 化执行**）+ must 最高（0.16）+ letMe 0.80（I 系推进）+ potential 缺失（3 次，提示词未含"预判"）。微观属"验证-修复驱动"型——but/actually/hmm 句首高（自我纠正频繁），但**黑屏漏网证明验证量再大也救不了"验证对象 ≠ 真实运行路径"**；用户修复后评级"还行"。
- **BB（不行：目录+渲染问题）**：**letMe=6 / we 家族 566 / we should=18（三项全会话最优档）**——Git Bash 首轮锚定的 we 型轨迹比 UP 更"纯"，但**轨迹纯度与渲染 bug 数无关**（flipY 全黑 + 用户实机的区块/破坏残留问题）。**预判修正**：potential=21（0.13/1k tok，除 UP/UP2 外最高，与 B3 并列）+ could=215（1.31，全会话第二）——预判密度第二高，预判的全是**已知风险点**（AO/碰撞/性能/指针锁定/透明排序），flipY 是**框架默认值类 bug（CanvasTexture flipY=true）不在预判清单**，靠 40+ 块像素级排查定位——**诊断强（材质替换隔离链、"That's it!"顿悟）但"未知 API 默认值"类风险无预判手段**。加上目录事故（MSYS/Windows 双路径，20+ 块推理消耗），BB 是"工具约定缺失 + 轨迹完美 + 预判盲区（框架默认值）"三因素叠加的对照样本。
- **RL（较好：anchored-standard-open 首跑）**：**轨迹中间带**（we 1.74 / let me 0.26——介于 anchored 带 2.6–3.4 与 standard 带 0.5–0.9 之间）+ **验收确认型语言**（fine 1.31 全会话次数第二、hmm 0.07 最低档、句首 Good/Fine）——"快速检查、频繁确认、很少悬置"。**let's 搭配 100% 执行类**（check/test/do/add/write）。potential 0.14（与 BB/B3 并列第二档）——预判了已知风险点，但**方向解算 bug 是"退化点验证闭合"盲区**：step 11 数学推导与 step 86 实测验证都只在 yaw=0 特例自洽（sin0=0 消掉交叉项误差），非零 yaw 的旋转顺序/符号从未被覆盖——**验证粒度细（像素/物理/控制台）但验证角度单一（默认朝向）**，与 BB flipY"框架默认值盲区"并列第二个盲区模式。水是唯一系统性设计+显式实现（游泳浮力）+持续验证的功能，用户实测可游泳、未报水渲染问题。
- **UP2（差：UP 同形态复测）**：**微观指纹与 UP 几乎全同**（见 5.6.0 表）——letMe=2、potential 1.41、we 家族 4.31（全会话最高）、maybe 2.93/fine 1.62（全会话双第一）、hmm 0.06（最低档）、情态合计 5.09（全会话最高档）——**"upstream 形态指纹"第二次完整复现**。验证行为：85 次工具调用中 40+ 为浏览器实测/像素断言（自装 python playwright + Edge headless + PIL 灰度分析 + tesseract 检查），验证量不小，但**单方块+区块渲染大故障漏网**——与 PA/BB 并列第三个"验证量充足但渲染坏"样本，且这是同形态下 UP 成功、UP2 失败的对照（见 5.6.0 结论 2）。水是唯一亮点（用户实测挖不掉+可填充+进水特效+游泳，12 会话最完整）——思维链 water 262 次（2.26/1k）持续关注，但 B1 water 更多仍可破坏，仅记录不引证。

### 5.7 对提示词工程的启示（微观脚手架）

在 standard-first-block-prompt 基础上可追加（可选）：
- 每个 `let me / let's / we can` 之后必须跟执行动词（check/test/write/verify/run/fix/patch/define）
- 禁止悬置句式：`let me also`、`let me think about`、`let me just`
- 每个里程碑先写一行 "Potential issue: ..." 枚举，再逐个验证
- 验证报告格式："我采样/断言了什么 → 观察到什么 → 对不对"（现象优先，不用"fine/ok"收尾）
- **方向/旋转/坐标类计算必须验证一般角度**（RL 教训）：除默认朝向（yaw=0）外，至少再断言 yaw=90°/180° 的期望位置——退化点自洽 ≠ 一般情形正确
- 涉及"框架默认行为"的代码（纹理 flipY/mipmap、旋转矩阵更新）在实现时写自检行（BB 的 flipY 教训）
- **"形态指纹可复现"不等于"质量可复现"（UP2 教训）**：同预设两次运行，轨迹/词形/预判全部复现，渲染大故障仍然出现——脚手架建议（如上）只改变表达层；**工程层质量（验证对象/粒度/角度、渲染管线自检）没有捷径**

## 6. 表达层变量与质量：脱钩与倾向（本实验最强归纳）

**核心结论（2026-08-16 全量回测后表述）**：本实验的所有干预变量（风格要求、cap、工具屏蔽、词形、shell 类型、锚定工具对、注入位置）都属于**表达层**（改变轨迹形态/语言风格/行为方式），而质量由**工程层**（首块规划深度、验证粒度/对象/角度）决定。12 个样本的最强归纳是**两轴独立**：

- **可被可靠改变的**（表达层）：风格要求（T2 生效 we=242/letMe=15）、注入方式（锚点消息 > system prompt）、轨迹形态（工具面持续时间决定）、语言风格（I/we 家族、情态密度、句首词）；
- **不被上述改变影响的**（工程层）：交付正确性。T2 风格最纯但贴图错；PA 提示词 1:1 执行（26 测试红→绿）但黑屏漏网；BB 轨迹最纯（letMe=6/we 566）最不可玩；B1 无注入无契约最好；**UP2 与 UP 同形态同轨迹（letMe 均 2、we 家族 3.32/4.31、potential 1.46/1.41）却 27.8 分 vs 85.7 分——排除预设差异后两轴仍独立**。

**各变量逐一结论**：

- **风格要求（T2 生效却贴图错）**：行为开关成立（语言轨迹可被契约改变），**质量开关不成立**（行为改变不传导到结果）——"即使 let me 消失也存在问题"（T2 实证）。
- **1024 cap（B1 有/UP 无都好）**：与质量无关联。
- **工具屏蔽（UP 受限仍交付）**：与质量无关联。
- **词形（I/we 两极都好）**：与质量无关联。
- **shell 类型与锚定工具对（BB）**：与质量无关联——轨迹完全复现（letMe=0、we 型），但渲染问题照旧；且新引入的 shell 是负资产（MSYS/Windows 双路径目录事故）。
- **锚定（首轮窄工具面）与质量：有正向共现倾向、无充分证明**：细则打分制下（见 2.3），好档（≥80）**3/4 在锚定组**（B1 86.8/UP 85.7/B3 80.0；非锚定组 T1 80.6 例外），差档（<60）锚定/非锚定各半（T2 35.7/T3 18.8 vs BB 5.0/UP2 27.8）——**倾向性引证**；但同条件反例（B2 71.1 与 B3 80.0 同预设：一低一高；BB 同锚定：5.0 分；UP2 与 UP 同形态：27.8 vs 85.7）排除充分性。且锚定组 7 会话用了 6 种不同预设形态，无"同预设 ± 锚定"配对对照，**无法分离锚定与预设形态的贡献**。
- **锚定效应与轨迹：充分成立（但轨迹 ≠ 质量）**：工具面持续时间决定轨迹形态（RL 晋升即回归 standard 系；旧 anchored 全程小工具面保持 minimal 轨迹）——这是表达层内充分可复现的效应，但 BB 证明轨迹复现 ≠ 质量复现。

**新增变量（RL）**：**首轮接口严格官方 minimal（[bash, str_replace_editor] + 一句 persona + 零注入）+ 晋升后全开**——机制全部按设计工作（request/header 实测逐字节一致、无 resident 隐藏组件、无路径事故），但**"首轮锚定"只产生微弱轨迹残留**（we 1.74 / let me 0.26 中间带），打分 71.1（中档）。**修正：轨迹锚定不是 schema 的一次性效应，而是工具面约束的持续效应**——旧 anchored 全程小工具面 → 全程 minimal 轨迹；RL 晋升即 63 工具全开 → 轨迹立即回归 standard 系。首轮接口纯净性、晋升全开、轨迹形态三者解耦：接口纯净 ✓（request 实测）、晋升全开 ✓（63 工具）、轨迹锚定仅首轮（设计使然）。

**新增变量（UP2，同形态复测）**：**预设形态与 UP 逐字节一致（首轮 `[bash, str_replace_editor]` + 晋升低注入 5 工具 + 无 skill-catalog），轨迹/词形/预判指纹全部复现（见 5.6.0）**——这是本实验唯一一次"同一预设 × 同一任务 × 独立运行"：表达层 100% 复现，工程层质量未复现（85.7 → 27.8，渲染大故障）。**含义：预设（表达层）决定的是轨迹，不是质量；质量的决定因素在两次运行之间不可控（工程层验证/实现细节），n=1 的单会话质量评级不能外推为该形态的稳定能力。**

## 8. 对下一轮实验的建议

> 以下建议基于本组样本的**共现观察**，未做配对对照验证，效果未知；仅作为下一轮实验的假设候选，不是已验证的工程方法。

1. **验证指令注入**（比风格指令更可能与质量共现）：要求像素级/几何级断言（B1/UP 本样本中共现；PA 反例说明指令执行 ≠ 验证对象正确，须同时约定"验证对象 = 真实运行路径"）
2. **微观脚手架**：代词后必须跟执行动词；禁 let me also/think/just；每里程碑先枚举 Potential issue（描述性建议，未验证）
3. **思考节奏**：长思考合法但必须闭合为动作；未闭合 = 被中止风险
4. **渲染质量验证补课**：mipmap 混色、半格错位、全透明均漏过现有验证——验证清单需含"纹理 tile 正确性 + 几何对齐"断言
5. **自定义 shell 工具必须显式约定路径格式**（BB 教训）：工具描述写死"文件工具只收 Windows 路径、bash 输出 MSYS 路径、转换表如下"，并在 execute 层兜底转换 workdir——否则模型会把 bash 输出路径直传文件工具造成目录错位
6. **纹理约定自检**（BB 的 flipY 教训）：涉及纹理/UV 的代码应在实现时写"UV 坐标约定 + flipY/mipmap 设置"的自检行，而非依赖事后像素排查
7. **交互/方向类验证补课**（RL 教训）：方向、旋转、输入映射类代码必须验证**一般角度**（至少 yaw=0/90/180 三点断言期望位置），默认朝向自洽 ≠ 一般情形正确
8. **anchored-standard-open 验证结论**：若目标是"严格官方 RL 接口开局 + 之后全开"，本预设达成且无缺陷（首轮 request 逐字节一致、晋升全开、无路径事故）；**若目标是全程 minimal 轨迹（modeltest 96-99 带），必须保持小工具面不扩大**——轨迹锚定是工具面持续约束的效应，不是一次晋升能锁定的
9. **若要证明任一变量的"充分提升"（当前不可证）**：最小设计 = 同一预设 ± 单一变量配对对照（如标准预设 vs 标准预设 + 首轮锚定）、n≥3、同一任务同一平台、盲评——否则只能停留在本报告的"倾向性引证"层次
10. **同形态复测已做、仍不足**：UP2 提供了第一次同预设复测（轨迹全复现、质量未复现）——它证明"预设→轨迹"是稳定映射，也证明**单次质量评级不能代表形态能力**；下一轮若想定位质量决定因素，需要"同预设 n≥3"并记录每轮的工程层细节（验证对象清单、渲染自检项），才能分离随机性与系统因素
